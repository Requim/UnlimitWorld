## 1. 确认与完成边界

用户已确认：当前缺少真正的攻击效果与动作，需要补齐；
世界观为庄严壮阔、有压迫感的国风神话，魔改中带有怪诞幽默；
采用高清精绘 2D、序列帧动作、分层场景，先做「章莪山·毕方」一场样板。

本文件将该方向具体化为入口、剧情数值、资源和表现协议细则。
2026-10-09 用户在本设计归档后明确要求「直接开始实施」，按本文件执行。
对应实施任务见 `../plans/2026-10-09-myth-bifang.md`。
实施授权不等于新生成种子的视觉认可；种子获认可前不展开动作和卡面批量生成。

目标交付是一场手机和电脑浏览器可实际操作的完整战斗：
流派选择、神话引入、剧情选择、战斗、胜负结算、重开和刷新续玩。
用户认可实际画质与动作后，才扩展其他怪物和章节。
既有九层局不删除，不把一场样板冒充整个 M5 已完成。

## 2. 现状与设计选择

- 原有 27 张位图通过文件解码、布局和引用检查，但用户否定其美术品质。
- 当前 Phaser 场景绘制静态角色，并对事件文字作 tween；
  没有完整的角色出招、受击、护盾和雷罚表现。
- 原表现只取最后三个事件，还会在更新时销毁动态层；
  新样板必须完整消费有序事件，不能丢失连击与最终击杀。
- 既有 Python 权威规则、SQLite 原子动作、网络幂等恢复及三流派保留。

选择高清精绘 2D 与序列帧动画，不切换 3D，也不在首样板引入骨骼编辑器。
React DOM 负责文本、卡牌与菜单，Phaser 负责世界、角色与战斗演出。
重构仅限样板必需的表现队列、资源布局和可复用剧情边界，函数不超过 50 有效行。

## 3. 神话依据与原创魔改

核对对象为《山海经·西山经》的章莪山段落：
山中无草木、多玉石；毕方外形似鹤、独足、青身赤纹、白喙，与火灾征兆关联。
保留这些识别特征，不把毕方画成双足凤凰，也不复制现代作品的角色设计。

来源：

- 中国哲学书电子化计划：`https://ctext.org/shan-hai-jing/xi-shan-jing/zh`。
- 维基文库《山海经·西山经》：
  `https://zh.wikisource.org/wiki/山海經/西山經`。

2026-10-09 已取得两站章莪山段落的检索正文；
CTEXT 页面直接打开返回 403，不记录为成功抓取全文。
原典与游戏改编分开记录，生成提示不借用现成游戏或影视角色。

原创故事：天道将章莪山的火灾归罪于毕方。毕方坚持自己只是火灾预兆，
为了证明没有纵火，竟烧毁了指控卷宗；修士被要求为灰烬作证。
其威严、危险与一本正经的荒诞逻辑并存，幽默来自行为因果而非 Q 版外形。
该故事、火羽招式和天道问责制度均为本游戏改编，不声称出自原典。

## 4. 入口、剧情与战斗规则

### 4.1 独立样板入口

- 新增同源 `/myth` 试玩入口，首屏直接选择流派并进入样板，不建营销页。
- `/` 的九层局和既有存档保持可用；样板使用独立的浏览器存档键，
  不覆盖九层局的 run ID 或访问凭据。
- 创建接口新增可选模式 `classic | myth_bifang`，省略时仍为 `classic`。
- `myth_bifang` 为正式服务器支持的体验模式，不是可上传数值的调试入口。
- 流程为三流派选择、剧情选择、毕方战斗、胜负结算和显式重开。
  样板地图只含一个毕方节点，不伪装成九层路线。
- 既有 SQLite 局面 JSON 缺少模式字段时按 `classic` 读取；
  新字段和剧情选择随存档持久化。实现前备份本地数据库，不承诺旧代码
  能直接读取新增字段；回退必须使用兼容读取或该实施前备份。

### 4.2 三个有后果的选择

所有收益与代价提交前完整展示，服务端验证并只结算一次。
选择只影响本场，不产生跨局永久属性，也不引入隐藏随机惩罚。

| 选择 | 原创剧情表达 | 开战条件 |
|---|---|---|
| 借火验案 | 向毕方借火，重演当年的案发现场 | 玩家天谴 +16；毕方初始燃烧 3 |
| 封存灰证 | 给灰烬贴上封条，要求双方保持冷静 | 玩家初始护盾 10；毕方初始护盾 6 |
| 毁卷结案 | 宣称卷宗不存，指控也应不存在 | 玩家首回合灵力 4；毕方下一次真实攻击每段 +2 |

修正值在建立战斗后应用，以免被初始化清空。
第三项攻击加值使用现有待消耗攻击加值规则，防御行动不消耗。
重试、刷新与重启不能重新获得开战收益。
选择 ID、内容版本和战斗修正由服务器保存，客户端不解析故事文字计算效果。

### 4.3 毕方行为与原规则

- 玩家仍为 60 生命、每回合 3 灵力、抽 5 张；牌堆、弃置和消耗规则不变。
- 样板十张初始牌组为 4 飞剑、3 护体、1 凝神及两张流派牌：
  御剑为蓄剑与万剑归宗，业火为火种与借火，符箓为照妖镜与引雷符。
  只改变样板牌组组成，卡牌数值、经典模式初始牌组和抽牌随机源不变。
- 毕方为独立样板 Boss，初始最大生命 48；不加入经典九层局的随机敌人池。
- 行动固定循环：蓄焰获得 8 护盾；火羽造成 5 伤害且天谴 +3；
  烈羽双击每段 5 伤害。天谴附加条件沿用现有规则：
  敌方攻击结算后双方都存活才施加，盾挡伤害不免除该天谴变化。
  预告展示实际段数、护盾、最终伤害和天谴变化。
- 护盾清除、虚弱、反伤、燃烧和挑衅继续服从既有领域规则。
- 每 30 天谴触发 8 点雷罚，护盾和引雷可反制；生死仍只由服务端生命决定。
- 毕方胜利直接结束本场，显示选择对应的改编结局；失败记录本机因果。
  不发放九层局的普通三选一奖励，也不跳回旧路线。

## 5. 美术、动作和 UI

### 5.1 画面方向（写实方案已冻结）

修士为完整、可信的人物比例，面部、衣料与武器有清晰层次。
毕方显著大于修士，展翼轮廓与独足可辨，不用发光雾团遮住身体。
章莪山由裸露玉石峰、断裂石台、远山与火光构成；主舞台可站立，
不把原典无草木的场所直接改成普通松林。

色彩以炭灰、冷玉石和中性亮部为基础，青羽与朱红火焰形成对照，
少量金属色用于仪式和 UI 强调；不让整页读成单一暗蓝、紫蓝或棕金主题。
威压来自尺度、构图与光线，不能靠压暗、模糊或遮挡主体制造。
分层远景、中景、战斗地面采用真实位图；不新增装饰光球和泛用背景粒子。

### 5.1a 当前卡通方向（取代写实绘制语言）

以实际认可的卡通毕方为视觉基准：流动轮廓、鲜明色块、简化的分组羽毛、
有限阴影层次与少量绘画笔触；表情和姿态承担一本正经的搞怪，
不再强调真实羽丝、皮肤毛孔或衣料微纹理，也不全员幼龄 Q 化。

修士为可读的成年游方剑修，白灰衣袍、炭色内衣、青绿边饰和朱红绳结，
通过紧张但嘴硬的表情产生幽默；完整双足、手和剑尖必须可见。
章莪山保留无草木的裸玉石山、断裂地台和神话尺度，采用动画背景绘制，
不把幽默变成现代道具堆砌，不通过暗雾遮住战斗前景。

两张配套原图已取得并制作静态合成，尚未获得用户实际认可。
生成提示词仅以文本匹配风格，不能声称已上传毕方图进行身份条件化；
正式动作继续按 5.3 从获认可的种子生成完整 strip，不逐帧凭文字重画。

### 5.2 真实高清与生成边界

- 角色种子原图目标 `2048x3072`；场景原图目标 `3840x2160`，质量 `high`。
- 记录请求尺寸和实际解码尺寸，保留原始文件与摘要；
  不达目标时标记未达标，不把插值放大称为原生高清。
- 首轮只生成修士种子、毕方种子和场景各一张，供用户查看。
  种子获认可后才扩展动作，不重新盲目批量生成旧 27 图。
- 完整样板还需重做九张可入手牌的插画：飞剑、护体、凝神、蓄剑、
  万剑归宗、火种、借火、照妖镜、引雷符。卡面原图目标 `1536x1152`，
  延续认可种子的精绘风格；不把旧漫画卡图当作新方向完成。
  未进入样板的其余卡图不在本次生成范围，经典模式原资源保持可用。
- 继续使用用户指定 API 和原装 ImageGen CLI，默认请求 `gpt-image-2`；
  不擅自切换供应商、模型或所谓 4K 别名，不无限重试收费请求。
- 凭据只在临时进程环境中使用，不写进文件、Git、前端或普通日志。
- 角色需要真实 alpha；若当前模型不能原生输出透明图，
  使用单色去底并核验羽缘、发丝、白衣和武器，不假称原生透明。
- 新资产用独立目录与 manifest 保存，既有素材保留为回退基线。
  游戏引用的最终文件必须位于项目中，不能只放在生成工具缓存目录。

### 5.3 必需动作与特效

| 主体 | 必需动作 |
|---|---|
| 修士 | 克制待机、挥剑出招、结印施法、受击、倒地 |
| 毕方 | 克制待机、蓄焰展翼、扑击或释放火羽、受击、败退 |
| 法术 | 飞剑轨迹与命中、火羽飞行与落点、护盾出现与受击、定向雷罚 |

每个攻击动作必须含起手、释放和收势的姿态变化。
单纯平移、缩放、震动静态立绘或播放浮动文字不计为序列帧动作。
从认可的种子图生成完整动作 strip，统一角色身份、比例和站立锚点；
帧规格、帧数、时长与锚点记录在资源元数据中，精灵纹理按实际显示尺寸整理。
动作每帧的实际内容也须足够支持目标显示尺寸与设备像素比，
不能拿高清种子图的尺寸代替低清 strip 的验收。
逐帧检查身体结构、独足、手指、武器、翼形与透明边缘，再进引擎验证。

出牌先有角色动作，再出现法术，接着命中、护盾反应和受击。
普通动作目标 0.35-0.9 秒，每次提交的完整演出目标不超过 3 秒；
多段攻击保留段落节奏，不能只显示最后三条事件。
强镜头反馈只用于重击、雷罚和胜负；正常画面不持续闪烁或摇晃。
减少动态设置关闭震屏、强闪光与非必要运动，保留简短可辨的状态结果。

### 5.4 手机和电脑界面

- 同一套材质：玉石、金属与符印；标题为中文宋体气质，正文为清晰黑体。
  使用可随项目分发并附许可的字体，取得文件和许可前不增加外链字体依赖。
- 场景无装饰外框；顶部集中生命、灵力、天谴与敌方行动预告，
  底部为稳定尺寸手牌和命令，长故事、日志、牌组与设置收纳。
- 手绘卡面不承载模型生成文字；费用、名称、效果由 DOM 绘制。
- 桌面使用宽取景，手机使用更高的取景并重排角色锚点；
  不把当前 5:2 战场缩成手机上的细条，也不裁掉角色身体与主要动作。
- 布局只由一套共享几何计算驱动，DOM 目标与 Phaser 角色一致；
  缩放、换方向和动画期间都不得出现目标命中偏移。
- 点卡、点目标仍能出牌，拖拽不是唯一交互。开局、剧情和结算不额外堆叠浮动卡片。
- 设置保留静音、音量、减少动态；图标工具用既有 Lucide 与可读名称。

## 6. 架构、事件与失败处理

### 6.1 服务器职责

模式、剧情选择和毕方规则放在现有领域边界内的独立内容模块。
应用服务协调建局、选择与结算，不把 Phaser 或图片依赖带进 Python Domain。
现有经典模式、旧 M4 主线、微信配置、支付和生产数据库不在修改范围。

创建、查询和动作仍通过现有 REST API；新增模式和故事展示字段
需导出 OpenAPI 并重新生成前端类型，不在两端手写不同协议。
故事视图至少提供标题、正文、选择完整代价与已选结果，纯展示、不接真实 LLM。
未知模式、错误选择或错误阶段返回 422，存档不得改变。

`GameEvent` 在保留既有字段的基础上增加可选的 `source`、`card_id`、
`visual`、`absorbed` 与 `state_after`。它们分别表示来源主体、卡牌来源、
表现类别、实际盾挡量与该事件后的公开战斗属性；不包含牌堆顺序或随机种子。
服务器按实际结算顺序产生事件，攻击完全被盾挡时也必须有命中和挡伤事件。
前端依据结构化字段选择动作，不通过中文文本匹配推断谁攻击、谁受击。
伤害、资源、随机源和生死仍只在服务端计算，不新增客户端规则上传接口。

### 6.2 前端职责

- 权威局面立即保存；表现层从上一显示快照消费有序事件，最后同步权威结果。
- 同一次动作的 `(run_id, revision, event_index)` 作为表现身份。
  精确重试、刷新同步及资源重新附着不能重复播放旧攻击。
- 演出期间禁止再次提交战斗命令，网络未决锁和演出锁分开管理。
- 最后一击即使将服务端 phase 改为结算，也必须先播放击杀与败退；
  不能因 React 切换视图而提前销毁角色。
- 新局、页面卸载、资源重试或场景销毁时取消旧队列、tween 和回调，
  旧局迟到事件不能覆盖新局。设置窗口不制造额外攻击或改变规则。
- 队列结束或失败都释放表现锁；演出错误显示恢复入口并同步权威局面，
  不重新提交出牌、伪造胜利或默默新开局。

### 6.3 失败与性能边界

图片失败保留权威局面，显示独立重试；缺少正式动作资源时标记样板未验收，
不用占位图或静态移动伪装完成。
未知网络结果沿用原编号和 payload 重试；409 只同步当前局面，
401 显示凭据恢复处理，所有生命周期保护继续适用。

资源按当前样板加载，压缩和分辨率选择不牺牲主体清晰度。
运行纹理与原始生成文件分离，测量手机解码、纹理与首战耗时，
不以固定提高构建警告阈值解决已有 Phaser 包体风险。
没有生产发布、旧账号迁移或全服联机授权，不操作生产服务。
